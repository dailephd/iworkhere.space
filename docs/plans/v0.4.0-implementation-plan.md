## 6. Canonical category architecture

### 6.1 Duplication found by retrieval

Category identity is currently spread across independent hand-maintained
places:

1. `ToolCategory` union in `type.ts`;
2. route-local `VALID_CATEGORY` array in the category page;
3. route-local `formatCategoryTitle()` switch;
4. route-local `categoryDescription()` switch;
5. a hardcoded valid-category array inside `registry.test.ts`;
6. category color rules in `theme.css` (one rule per id).

`getAvailableCategory()` is correctly registry-derived and is not an identity
source. Nav labels, breadcrumb labels and home chips derive a display label by
capitalizing the id; they are not lists and remain unchanged.

### 6.2 Frozen design

Create one category-definition module in the tool domain
(`src/module/tool/category.ts`; exact filename fixed in the Batch 1 prompt
only if retrieval shows a conflicting name). It is the single runtime owner
of:

- canonical category ids (as a typed `as const` list);
- canonical order;
- page `title` (what `formatCategoryTitle()` returns today);
- `description` (what `categoryDescription()` returns today);
- runtime validation (a type guard such as `isToolCategory(value: string)`) and
  definition lookup.

Rules:

- `ToolCategory` is derived from the canonical list
  (`(typeof list)[number]["id"]`) and re-exported from `type.ts` so existing
  `import type { ToolCategory } from "./type"` sites keep working. There is no
  second hand-maintained union.
- Canonical order is exactly today's observable order
  `document, text, math, everyday, time, image` with `developer` appended
  last. `getAvailableCategory()` still derives populated categories from
  `tool_definition_list` but returns them in canonical order. A test pins the
  pre-change order so this is provably not a behavior change for the six
  existing categories. Reordering categories is a separate product decision
  and is out of scope.
- The category route stops owning `VALID_CATEGORY`, `formatCategoryTitle()` and
  `categoryDescription()`; it validates with the guard, resolves title and
  description from the owner, and keeps `notFound()` for unknown slugs. Titles
  and descriptions for the six existing categories are moved verbatim (route
  output unchanged).
- The registry remains the authority on which categories are populated. A
  category appears in nav, home chips, the sitemap and Discover only when a
  registered tool uses it.
- No separate short-label field is added: nav/breadcrumb/chip labels remain
  id-derived by capitalization, which yields "Developer" correctly. Adding a
  label field would create a second source.
- `registry.test.ts` stops hardcoding a category array and imports the
  canonical list.
- No dynamic discovery, reflection or auto-wiring; explicit imports only.

### 6.3 Category presentation tokens (added scope found by retrieval)

Category identity also drives color: `theme.css` maps `[data-category]` to
`--category-<id>` / `--category-<id>-soft`. A populated `developer` category
therefore needs those tokens in every theme (Light, Dark, One Dark; System

section), the new tokens consume the existing token structure, contrast is

introduced. This is a token addition, not a visual-system redesign.

## 8. JSON Formatter / Validator contract

- **Input:** strict RFC 8259 JSON text. Any value is a valid root: object,
  array, string, number, `true`/`false`, `null`.
- **Rejected:** comments (JSONC), trailing commas, trailing content after the
  root value, single quotes, unquoted keys, NaN/Infinity, leading zeros, raw
  control characters inside strings, a leading BOM, and empty or
  whitespace-only input (no root value). JSON whitespace is only space, tab,
  LF, CR.
- **Operations:** Format (2-space indent), Minify, Copy result, Reset. No
  configurable indent, sort or other formatter options.
- **Lexical preservation (critical):** output is produced from the validated
  token stream, not from a parsed JavaScript value. `JSON.parse` →
  `JSON.stringify` is forbidden as the formatting path because it coerces
  numbers through `Number`, normalizes exponent/precision, re-escapes strings
  and collapses duplicate keys. Only insignificant whitespace may change.
  Number lexemes, string lexemes (including escapes such as `é`, `\/`,
  `😀`, and lone-surrogate escapes), literal tokens and member order
  are emitted verbatim. Duplicate object member names stay as written.
- **Pretty layout:** `{`/`[` then newline and indent per entry, `"key": value`
  with a single space after the colon, `,` then newline between entries,
  empty containers as `{}` / `[]`, no trailing newline. Minify emits no
  insignificant whitespace.
- **Algorithm decision (no dependency):** a small in-repo pure module
  implements a strict scanner/validator with an explicit stack (iterative, so
  1 MiB of nested `[` cannot overflow the call stack) and a token-preserving
  emitter. No third-party JSON library is added: the lexical-preservation
  contract is small, well-specified, and fully testable, and a dependency
  would add review surface for no gain.
- **Errors:** invalid input yields a structured result with a stable error
  `code`, our own bounded message (never echoing input text), a zero-based
  character `offset` (UTF-16 code units), and 1-based `line` and `column`
  (line breaks LF, CRLF, CR). The public contract never depends on engine
  `JSON.parse` wording. Invalid input produces no output at all; output is
  cleared.
- **Resource boundary:** maximum input 1 MiB UTF-8 (1,048,576 bytes, measured
  with `TextEncoder`); exactly 1,048,576 bytes is accepted, one more is
  rejected locally with bounded feedback before scanning.
- **Privacy / state:** browser-local; no upload; no persistence; no query state
  carrying input; telemetry is identity-only (`tool_executed`,
  `tool_result_copied` with `{toolId, slug}`); `captureError` meta contains no
  input or output.
- **Out of scope:** JSON Schema, JSONPath, tree editor, YAML/XML conversion,
  key sorting, syntax-highlighting editor, URL fetch, cloud storage.
- **UI:** follows the existing text-tool precedent (labeled input textarea,
  read-only output textarea, Format / Minify / Copy / Reset buttons, error
  region announced with `role="alert"`). No new shared UI framework.

## 9. Word / Character Counter contract

Metrics (exactly four, updating live from the current input):

- **Words**: `/[\p{L}\p{N}][\p{L}\p{M}\p{N}]*(?:['’][\p{L}\p{N}][\p{L}\p{M}\p{N}]*)*/gu`
  semantics. A word is a contiguous run of Unicode letters/numbers (combining
  marks attached inside a run stay in it, so decomposed accents do not split a
  word). One straight (`'`) or curly (`’`) apostrophe between two such runs
  joins them (`don't`, `don’t` = 1). Surrounding punctuation is excluded.
  Hyphenated terms are separate words (`well-known` = 2); underscores,
  slashes and emoji are not word characters. Locale-independent and
  documented in the tool guide.
- **Characters**: user-perceived characters = Unicode extended grapheme
  clusters via `Intl.Segmenter` with a fixed locale (`"en"`, granularity
  `"grapheme"`). Combining sequences and emoji ZWJ/flag/skin-tone sequences
  count once. UTF-16 `length` is never used.
- **Characters excluding whitespace**: the same grapheme units minus graphemes
  whose every code point is `\p{White_Space}`. Zero-width characters that are
  not `White_Space` (for example U+200B) count; this is documented.
- **Lines**: empty input = 0; otherwise (number of CRLF/CR/LF separators) + 1,
  with CRLF counted as one separator. Consequently a trailing newline starts
  a new (empty) line (`"a\n"` = 2). Unicode LS/PS/NEL are not separators.
- **Browser support:** feature-detect `Intl.Segmenter`; if unavailable, show an
  explicit unsupported message instead of falling back to code-unit counting
  (a fallback would violate the contract). The implementation prompt
  confirms current evergreen support and the repository's browser stance
  before coding.
- **Behavior:** Reset clears input and returns every metric to 0. No server
  request, no persistence, no shareable query, identity-only telemetry
  (no metric values required).
- **Resource boundary:** maximum input 1 MiB UTF-8; over the limit the tool
  shows bounded feedback, computes no metrics, and keeps the input so the
  user can edit or Reset.
- **Out of scope:** sentence count, readability, keyword density, reading
  time.

## 10. QR Code Generator contract

- **Input:** one text field: plain text or URL text. URLs are never fetched or
  visited. Payload is used exactly as typed (no trimming or normalization).
  Empty input (length 0) generates nothing. Maximum 2048 UTF-8 bytes
  (`TextEncoder`); exactly 2048 is accepted, 2049 is rejected locally with
  bounded feedback.
- **QR parameters (fixed):** UTF-8 byte-mode payload; error correction level
  `M`, with automatic ECC boosting explicitly disabled so the level can never
  silently exceed `M`; black foreground on white; standard quiet zone.
- **Output:** 512 × 512 px PNG. Drawing rule: module scale =
  `floor(512 / (modules + 8))`, symbol centered, white background, which
  guarantees an integer module size and a quiet zone of at least 4 modules.
  The preview is the generated canvas scaled by CSS only (responsive,
  `max-width: 100%`); generated output identity stays 512 × 512.
- **Interaction:** Generate (create/update the preview), Download PNG
  (`qr-code.png`, enabled only for a current generated code), Reset. Editing
  the input after generating clears the preview/download so stale codes cannot
  be downloaded. Object URLs are revoked on replace, Reset and unmount.
- **Caveat documented in the guide:** a maximum-size payload yields a dense
  symbol (about 2 px modules in a 512 px PNG) that is valid but harder to
  scan; short payloads scan best.
- **Privacy:** local generation; payload never leaves the browser and is never
  placed in analytics/log/`captureError` payloads; no storage; no
  shortener; no query state.
- **Out of scope:** logos, colors, themes, Wi-Fi/vCard/payment/calendar
  payloads, URL shortener, dynamic or tracked QR, cloud storage, bulk mode,
  SVG export.

## 11. QR dependency decision

Evaluated against the package registry on 2026-10-07; generation and decoding
of 11-byte, URL, Unicode, 2048-byte ASCII and 2048-byte multibyte payloads were
verified empirically in a throwaway directory under the project-contained
workflow root (never in the application).

| Package | Version | License | Runtime deps | Notes |
|---|---|---|---|---|
| `uqr` | 0.1.3 (published 2026-04-03) | MIT | none | ESM, `sideEffects: false`, ~27 KB dist (~7.8 KB gzip); explicit `ecc`, `border: 0`, `boostEcc`; returns a boolean matrix (we draw the canvas). Round-trip decoded correctly for every probe payload. |
| `qr` (renamed `@paulmillr/qr`) | 0.7.2 (modified 2026-09-28) | MIT OR Apache-2.0 | none | Actively maintained; ~44 KB (~14 KB gzip); raw output always includes a border (min 1/default 2) which must be stripped; also ships a decoder. Round-trip decoded correctly. Documented fallback. |
| `qrcode` | 1.5.4 (2024-08) | MIT | `pngjs`, `yargs`, `dijkstrajs` | Node-oriented; CLI/Node dependencies unnecessary for a browser tool. Rejected. |
| `qrcode-generator` | 2.0.4 | MIT | none | ~555 KB unpacked, legacy API. Rejected as heavier than needed. |
| `qr-code-styling` | 1.9.2 | MIT | `qrcode-generator` | Styling/logo features are out of scope. Rejected. |
| `@paulmillr/qr` | 0.3.0 | — | — | Deprecated in favor of `qr`. Rejected. |

**Selected production approach: `uqr`.** It meets the fixed contract, has no
dependencies, no Node/native/server surface, and the smallest browser cost
(loaded only on the QR tool route). Caveat: version 0.x from a smaller project;
mitigated by exact version pinning, the independent decode test below, and the
documented `qr` fallback (switch only if `uqr` fails a contract test or is
unmaintained at implementation time).

Implementation-time rule: Batch 3 re-resolves the current registry state,
pins an exact version (no caret) of the chosen package, re-confirms license,
dependency list and the contract probes, and updates `THIRD_PARTY_NOTICES.md`.
No dependency is installed during planning.

**Test-only decoder: `jsqr` 1.4.0 (Apache-2.0, published 2021, unmaintained but
test-only).** It is independent of the encoder library. It is a
`devDependency` pinned exactly at Batch 3 and never imported by production
code. It decodes RGBA pixel data, so no PNG-decoding dependency is needed
(browser test draws the downloaded PNG to a canvas in the page and passes
`ImageData` to Node). If `jsqr` is unavailable or fails at implementation
time, the batch stops and escalates rather than weakening the correctness
test.
