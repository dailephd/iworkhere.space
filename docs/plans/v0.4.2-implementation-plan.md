## 2. Human-report taxonomy and form

Offer these mutually exclusive primary categories, with optional category-specific subreason: incorrect_result, tool_failure, invalid_output, interface_accessibility, performance_compatibility, content_link, privacy_security, suggestion, other.

Examples: incorrect mathematical/converted/time results; action fails or produces no download; corrupt PDF/missing pages/wrong image output; controls overlap, focus/keyboard/contrast defects, anchored chrome hides content; slow/frozen tool or browser-specific failure; wrong instructions/broken links; suspected exposure or security weakness; requested new utility, additional format, usability enhancement.

One site-wide entry point named "Report a problem or suggestion" must be available from every public page, including while the footer is retracted. Default tool and canonical pathname context derive from the registry/current page, with a user-editable "Where did it happen?" selector if the inferred context is wrong. Never infer a nonexistent tool or create a second tool registry.

Fields: report category (required); affected area/tool (required, including Site-wide/Other); description (required, up to 2,000 Unicode characters); expected behavior (required for incorrect-result reports, optional otherwise, up to 1,000); observed behavior/example (optional, up to 1,000); optional contact email (up to 254, validated); explicit contact consent (off by default). For suggestions, replace expected behavior with "What improvement would help?" and optional suggested use case. Provide inline assistance, never solicit original files, secrets, full URLs, passwords, private documents or exploit payloads. Warn accordingly for privacy/security.

Automatically include only allowlisted pathname without query/hash, canonical tool ID when resolved, coarse viewport class, error-free browser compatibility family when explicitly disclosed, safe deployment/release identifier provided by server, and server receipt time. Do not attach input values, formulas, text, local storage, filenames, PDF/image bytes, generated output, page query/hash, cookie, authentication headers, arbitrary device fingerprints or raw exception data. No uploads, screenshots, session replay or automatic reproduction data collection in this patch. Human text stays in the protected support domain and is never emitted through /api/metric, /api/log, Vercel Web Analytics or the application error telemetry facade.

Form is an accessible dialog or similarly accessible overlay: heading/labels, expected/observed conditional fields, keyboard focus management, Escape/close, live validation without surprise, visible retry state, prevention of duplicate clicks, return focus to the originating trigger, and a receipt with opaque report reference. Do not clear a user's draft upon a failed submission. A rejected/failed submission must never display a false success. Do not persist the narrative/email to browser storage.

## 3. Persistence and API contract

Create a separate support domain and database schema, NOT new rows/columns in the observability metric or diagnostic tables. The existing Neon project may be reused, but support has dedicated database roles, credentials and grants. It must not reuse the observability writer or dashboard read-only credentials for support mutation.

Planner-assigned ownership and destinations:
- src/module/support/ — shared typed support request/response contract, validation, canonical context projection, redaction, idempotency and domain operations.
- src/app/api/support/report/route.ts — thin POST HTTP adapter, no domain logic.
- database/support/ — numbered additive SQL migrations, least-privilege grant templates, support retention/operation README. No changes to numbered observability migrations.
- src/module/support/persistence.server.ts — server-only support submission and outbox transaction.
- src/module/support/delivery.server.ts — server-only delivery worker, provider adapters and retry policy.
- src/app/api/support/deliver/route.ts — cron-secret-protected delivery/retention adapter.
- src/component/support/ — report form/dialog and state; a single site-wide trigger composed through existing AppShell shell ownership.
- dashboard/src/lib/ and dashboard/src/component/ — required support-specific read-only query and private report-detail presentation within the existing protected separate dashboard, with a separate SUPPORT_DASHBOARD_DATABASE_URL SELECT-only credential.
- docs/API.md, docs/SCHEMA.md, docs/OBSERVABILITY.md, docs/DEPLOYMENT.md, docs/TESTING.md, docs/DESIGN.md, docs/doc_index.md, docs/project-status.md, privacy disclosure and support database README — update only the affected current contracts during implementation/documentation reconciliation.

Strict POST payload: only versioned category, tool/area, pathname, description, expected/observed, optional email/contact opt-in, one random idempotency key, and an ephemeral Cloudflare Turnstile challenge token; reject unknown keys. The challenge token is verified server-side, never stored with the report and never logged. Maximum request body 16 KiB, explicit field bounds, valid category/tool IDs, no query/hash, and unambiguous normalization. Server creates opaque report ID and timestamp. Require same-origin request checks plus a separately enforced production bot/abuse control; header checks alone are not authentication or rate limits.

One SQL transaction inserts the durable report and independent outbox delivery items. Reuse idempotency key on client retries; unique server constraint ensures the same request cannot create another report or multiple outgoing jobs. Successful persistence returns 201 with the stable opaque reference even if notifications are temporarily down. Validation returns 400; abuse/limit cases return 429; failed persistence returns safe 503 with no success ID. All response fields are strictly bounded; no raw SQL, vendor secrets or report narratives in logs. API routes must be network-only under the existing service-worker policy.

## 4. Private triage and notification architecture

Persistent support storage is the source of truth for the original submitted report, contact consent and delivery records. The existing observability schema remains the source of truth for technical telemetry. Do not add user-report text to existing diagnostic tables. The dashboard's existing observability connection stays SELECT-only and unchanged.

Private issue lifecycle owner: GitHub Issues in an operator-provisioned PRIVATE support repository. The public application's existing public source repository is forbidden as an automatic issue destination. Triage labels/states: new, investigating, accepted/planned, resolved, duplicate, not planned, and security-priority; preserve the private tracker URL on the report record. Do not copy the user's free-form narrative or contact details into GitHub issues. Create private issues containing only report ID, category, canonical tool/route, internal dashboard link and submission timestamp. GitHub issue state owns the investigation/closure lifecycle; do not maintain a falsely synchronized second issue-status authority in Neon. The protected dashboard reads the full reports under a dedicated SELECT-only role and links to their private tracker issues, but its current app itself must not gain write privileges.

Resend is selected for transactional operator notification, and optionally a consented contact receipt, through a server-only adapter. Emails contain report ID, category and secure triage location, not raw descriptions, contact details, tool inputs or files. Use dedicated verified sender/domain credentials, explicit opt-in for contact, rate and delivery monitoring. No in-browser Resend secret.

The support outbox must retry failed private-issue creation and failed email notification independently, and must expose failure counts/oldest-pending age to the protected operator view so silent delivery outages are detectable, with idempotent provider interaction where supported, bounded attempts/backoff and a visible failed/dead-letter operational state. On provider timeout, reconcile against existing private issue IDs/markers before a second create. Delivery cron must be separately protected, avoid logging original report bodies and never delete accepted reports because a provider fails. The intended notification/triage delivery target is within 15 minutes in normal service; if the deployed hosting plan cannot schedule/operate the worker at that cadence, resolve the hosting/queue contract before production launch rather than claiming the target is met. A missing external provider or credentials is an explicit deployment blocker, not a mock production mode.

Abuse boundary: production server-side volume limits and bot protection are mandatory. Proposed provider is Cloudflare Turnstile with server verification plus Vercel Firewall/rate policies where available; provider-specific activation/privacy must be tested and documented. Do not silently use application-stored IP addresses or create application-side user/session tracking. Do not expose raw reports to public APIs, sitemap, analytics or public GitHub repositories.

Retention target for design review: report narrative 180 days after receipt and contact email no longer than 90 days after last authorized correspondence, subject to the finalized privacy/legal policy and operational purge job. Implement only after the disclosure, deletion/exception behavior and testable retention clock are finalized. The privacy notice must describe stored voluntary content, processing vendors and relevant contact/retention details before the public form is enabled.

## 5. Header viewport-retraction behavior

AppShell and the existing Header/VerticalNav remain the only shared layout/nav owners. Original header is in normal document flow at the top. Its scroll-out-of-view detection is based on a header sentinel or equivalent viewport intersection, not a timer or arbitrary page scroll threshold.

When the original header remains visible, there is no replacement control. Once it has fully left the viewport, a small fixed top control labeled "Show navigation" appears. Clicking opens the same Header content as a fixed top overlay without scrolling the document to the top. The control becomes "Hide navigation"/close while open; Escape and choosing a navigation item close it. Returning to the page top reverts to the ordinary in-flow header. Header expansion/collapse must preserve scroll position, theme state, one primary navigation landmark and one real header DOM subtree; do not mount a duplicate interactive Header/nav. Preserve the original header's layout footprint to avoid document jump and scroll anchoring regression. Do not turn the entire RootLayout or AppShell into Client Components solely to observe scroll. A focused client control may manage the viewport state. No animation library; reduced-motion safe transitions only.

In overlay mode the header must respect safe-area insets, viewport widths and route changes; focus must not disappear into visually hidden controls; it must not mask a modal report dialog or the skip link.

## 6. Footer viewport and retraction behavior

Existing Footer and AppShell remain presentation owners. The actual semantic footer is fixed to the bottom of the VISUAL viewport (not just the document end) on every public page, with responsive compact content and the existing copyright/privacy link. Add "Report a problem or suggestion" to the expanded footer. Default fresh-visitor state is expanded. A visible "Hide footer" button retracts the fixed footer to a slim, anchored bottom control that includes "Show footer" and a still-accessible "Report" action. Clicking "Show footer" restores the complete footer without changing scroll position. Footer preference persists across internal navigation and reload using the existing src/lib/storage.ts adapter, with deterministic safe fallback when storage is unavailable; prevent a visible hydration flash/layout shift.

Expanded footer should use minimal height and never exceed a documented mobile viewport occupation limit. Account for CSS safe-area bottom insets, software keyboard, overlays and short pages. Main content must have sufficient effective scroll clearance so the last field, result, download control, focus target and anchor can be brought fully above the fixed footer; do not implement a secondary main scrolling pane. Adjust document scroll-padding/scroll-margin and shell bottom clearance through one layout owner rather than individually padding each utility. Collapsed state restores workspace visibility. Footer advertising banner slots remain in ordinary document flow and must never become fixed, retracted invisibly or mixed into the footer control; keep advertising eligibility, reservation and privacy behavior intact. Provide access to Privacy Policy even when footer is collapsed (through expansion) and keep reporting reachable directly in both states.

Both header and footer controls have clear visible focus, aria-expanded and aria-controls against actual controlled content; keyboard and screen-reader semantics are tested. Layering order: ordinary content < fixed footer/header < focused report dialog; the skip link must remain accessible. Use the current six-palette semantic tokens without new one-off color systems.

## 8. Mandatory use cases and release gates

Reporting: one successful report from tool page and general page; optional/empty email; contact consent; all categories and conditional fields; incompatible/unknown tool; malformed/oversized/extra-field input; XSS rendering and data redaction; forbidden file/input fields absent from outgoing telemetry; double-click/retry same ID; abort/network interruption; DB down; Resend down; GitHub down; worker retry/dead letter; token/authorization failure; concurrent queue attempts; private dashboard protection and read-only roles; accessibility, disabled JS and mobile; host rate limit and bot challenge; outbound issue and email contain no user narrative; retention/delete; email credential missing; healthy database but failed notifications still acknowledged; false success impossible.

Header: top initial page, header partially vs fully outside viewport, rapid scroll, expand/close/return top, route navigation, focus traversal, skip link and one nav landmark, reduced motion, all responsive widths/themes, no scroll jump/hydration duplication.

Footer: fixed in short and long pages, expanded/collapsed, initial and persisted state, poor/storage-disabled case, document bottom scroll/focus visibility, anchors and downloads, mobile software keyboard/safe area, not obscuring reporting dialog, reserved space and CLS, privacy/report availability, footer advertising remains normal flow.

Production blockers: Neon support schema/grants deployed and audited; protected dashboard support read-only credential provisioned; private GitHub support repo and restricted token; Resend verified sender and token; Turnstile production challenge/verification and enforced abuse controls; job schedule/worker and failure recovery verified; privacy policy/provider disclosures reviewed; one synthetic report independently traced through response ID -> support storage -> private dashboard -> private GitHub issue -> notification, including one deliberate delivery failure/retry; deployment SHA recorded. Fail closed with honest status if any mandatory provider or test is unavailable.
